# 视图检索的条件区改造：工具栏 + 抽屉

> 解决的问题：24 个视图每个都有几十个可筛列，`ViewExplorer` 原先把**所有条件卡片**
> 平铺在结果表上方（`.fgrid` 一行 4 张卡片），条件越多页面越高，结果表被顶到屏幕外，
> 只剩不到一屏的一半可见。

## 1. 调研：条件多了怎么放

主流产品有四种安置方式（LogRocket《Designing better advanced search UIs》）：

| 方式 | 代表 | 代价 |
|---|---|---|
| 顶部工具条 | Jira、LinkedIn | 位置有限，只放得下少数条件 |
| 左侧栏 | Amazon、eBay | 常驻占宽，主内容变窄 |
| 可展开面板 | 多数 SaaS 后台 | 容易被忽略，需明显的入口按钮 |
| 全屏/抽屉弹层 | Airbnb 移动端、Airtable | 编辑时看不到结果，适合"批量应用" |

几条被反复强调的实践规则：

1. **只把最高频的 2–3 个条件放在外面，其余收进面板**（Innovaccer 表格筛选模式：
   "3 个以内直接放表格头；超过 3 个用 `+ 更多筛选` 打开右侧面板，面板关闭时
   始终保留前 3 个作为快捷筛选"）。
2. **面板要能搜索条件本身**——条件超过 15 项时，用户找不到该用哪一列，必须提供
   筛选器搜索（LogRocket 分面导航建议）。
3. **已应用条件用 chips 平铺展示、单个可删、另有"全部清除"**（Avalara 表格工具条、
   Innovaccer 都要求 chip 贴在表格上方）。
4. **筛选状态写进 URL**——可分享、可刷新、可前进后退（URL as State 模式）。
5. **频繁使用的筛选走"批量应用"，即时反馈的筛选要防抖**，避免每敲一个字打一次库。

## 2. 现成方案对比

| 方案 | 能力 | 适配本项目 | 结论 |
|---|---|---|---|
| `vue3-advanced-query-builder`（orakley） | 规则/操作符/自定义输入组件，递归 AND-OR 分组 | 输出是树形查询 DSL，而后端 `/api/view` 是**扁平 AND**；需把树折平 + 改协议 | 不采用 |
| `vue-query-builder` | 同上，但面向 Vue 2 | 版本不兼容 | 不采用 |
| `react-querybuilder` | 生态最全的跨框架 query builder | React only | 不采用 |
| Element Plus `el-table` + 列筛选 | 表头下拉筛选 | 需要把整页换成组件库表格，改动面远大于收益 | 不采用 |
| TanStack Table | 无头表格 + 自带列筛选/分面 | 只解决表格侧，条件区布局仍要自己写；引入 40KB+ | 备选 |
| **轻量自研（本次采用）** | 复用已有的 `view_meta.json` 列元数据 | 列的 kind/取值分布/关联键**已经声明好了**，前端只是渲染 | ✅ |

> 关键判断：本项目的"条件"是**每列一个 AND 条件**的扁平模型，没有嵌套 AND/OR 需求，
> 而 query builder 类库的核心价值恰恰是嵌套分组。引入它们属于过度设计；
> 真正要解决的是**布局与检索入口**，这部分没有现成组件能直接套。

## 3. 新布局：三区分离

```
┌── 视图头（一行）  视图名 · 行数/列数/可筛列数        结果数 · 上一页/下一页 · 刷新 ┐
├── 工具栏（一行，永远只有一行）                                                │
│  [⌕ 在所有文本列中搜索]  [快捷条件▾]…  [已选 chips ×]    预设 列 筛选(3) 重置   │
├── 结果区（flex 占满剩余高度，内部滚动 + 表头 sticky）                          │
│                                                                              │
└──────────────────────────────────────────────────────────────────────────────┘
                                                    ↑ 点「筛选」→ 右侧抽屉（420px）
```

- **工具栏**：全局搜索框 + 最多 3 个快捷条件（按 人物 → 年份 → 枚举 的优先级自动挑）
  + 已选 chips + 按钮组。工具栏自身不换行增高，条件再多也占一行。
- **抽屉**：点「筛选」从右侧滑出，含**全部**可筛列，按 kind 分成
  人物/年份/数值/枚举/文本五组；顶部可**搜索条件名**；底部「应用」「清空」。
- **浮层**：快捷条件点开是个小弹层，内容与抽屉里的控件**同一个组件**（`FilterControl.vue`），
  不存在两套实现。列显示、预设、按姓名定位也都走同一套浮层机制（同时只开一个）。

## 4. 具体改动

| 文件 | 改动 |
|---|---|
| `web/server.py` | `build_view_query` 新增 `any` 参数：`[{"cols":[…],"val":"x"}]`，组内多列 OR、与 AND 条件并列。用于支撑"一个搜索框搜遍所有文本列"（原先只能逐列 AND，做不了这个） |
| `web/frontend/src/components/FilterControl.vue` | **新增**。单个可筛列的条件控件，抽屉与浮层共用 |
| `web/frontend/src/components/ViewExplorer.vue` | **重写**。工具栏 + 抽屉布局；URL hash 同步；本地条件预设；结果区 flex 占满 |
| `web/frontend/src/App.vue` | `.content.flat`（视图模式外层不滚动）；新增 `open-view` 事件与 `readUrlState()` 深链恢复 |

### 全局搜索怎么实现

原先后端只支持"每列一条 AND"，做不了"任意列包含关键词"。新增的 `any` 让前端把
视图里所有文本/枚举列（最多 24 列）拼成一串 `col1 LIKE ? OR col2 LIKE ? …`，
再与其它 AND 条件组合。实测 `View_PeopleData` 搜「安石」→ 0.007s 命中
陈安石 / 王安石 / 王氏(陈安石妻)。

### 结果表的高度账

改之前：`条件卡片(fgrid 多行) + chips 行 + 结果表 max-height:480px`
→ 条件一多，结果表被挤到折叠线以下。
改之后：`工具栏 1 行 + 结果区 flex:1` → 无论几个条件，**结果表都吃掉整屏剩余高度**，
表头 sticky，内部滚动。

## 5. 顺带做掉的几件事

- **URL 深链**：`#view=View_KinshipGenealogyData&st={…}`，分享链接即可还原视图 + 条件 + 排序 + 页码。
  例：`http://127.0.0.1:8787/#view=View_PeopleData` 直接进视图检索模式。
- **条件预设**：调好的条件可存到浏览器（localStorage，按视图分别存），下次一键套用。
- **自动重查**：条件/关键词变化后 320ms 防抖自动查询，同时保留「刷新」按钮；
  加了请求序号（`seq`）丢弃过期响应，避免快速改条件时结果错乱。
- **空结果引导**：空态直接给「清除全部条件」按钮。

## 6. 还可以继续做的

- 抽屉里的枚举值按当前结果**动态分面**（现在用的是剖析样本的静态计数，不能反映已选条件后的余量）。
- 预设搬到服务端 / 导出为文件，跨浏览器共享。
- 快捷条件的选取现在按 kind 优先级硬编码；接入使用频次统计后可改为真正的"高频"。

# 第二轮：布局再压缩 + 列名中文化

> 两个新问题：
> ① 结果表占比仍然偏小 —— 左侧 260px 的分组树长期占宽，"视图名 / 库概况 / 模式切换" 各占一行；
> ② 条件区满眼 `c_office_chn` 这种库列名，新人看不懂；但中文和英文同时显示又会把表头挤乱。

## 7. 布局：把横向还给结果表

把 260px 的**常驻左侧栏**换成一行的顶部导航，这是成熟产品的常见路径：

- Canvas Catalog 2025-08-11 改版把 tab 导航换成**下拉菜单**，官方给的理由是
  「层级更清楚、移动端更好、能显示更长的名字、靠面包屑保持方位感」；
- 大目录（Navi+ / CommerceBolt）的通行做法是 **mega menu**：宽面板里分组列全量条目 +
  面板内自带搜索，配面包屑防止迷路；
- 表格侧（Ninja Tables / Frontend Genius）反复强调：**搜索框要贴近表格**（"proximity is trust"）、
  **表头 sticky**、**行密度可调**、**只显示 5–8 个必要列，其余放进「自定义列」**。

落地方案（结果区从"半屏"变成"整屏减 3 行"）：

| 原来 | 现在 |
|---|---|
| 顶栏 brand+副标题 2 行 + 模式条 1 行 + KPI 卡片 | **顶栏 1 行**（品牌 / 模式 / 概况 / KPI 内联） |
| 左侧 260px 分组树（吃掉 1/4 横向） | **导航条 1 行**（分组 tab + 视图下拉 + ⊞ 全部） |
| 独立「视图头」行（视图名·行数·翻页） | 并进导航条，**整行取消** |
| 「排序」下拉行 | **点表头排序**（升 → 降 → 取消），整行取消 |
| 工具栏 flex-wrap 可换行 | `nowrap`：chips 横向滚动，右侧统计/翻页永远可见 |

额外交互：行密度（`≣/≡`）、显示列开关（14/91）、Esc 关闭任意浮层。

## 8. 列名：主显中文，原始名按需露出

调研到的三条约束（彼此有张力）：

1. Retool 的表格指南直接点名：「别把库列名（snake_case）留在表标题上，用户读起来费劲」；
2. Siteimprove Fancy 的 ColumnHeader 建议：标签要简短，**补充信息（如缩写、专业术语）放 tooltip**；
3. Helios Design System 又警告：**别给几乎所有列都挂 tooltip**，会制造视觉噪音、抬高认知负荷。

所以既不能"满屏 tooltip"，也不能"到处双写"。采用**分档露出**：

| 位置 | 中文名 | 原始 `c_xxx` |
|---|---|---|
| 结果表表头 | 主显 | 默认不显示；hover 的 tooltip 里有；「列名」开关打开后追加灰色小字 |
| 右侧抽屉的筛选控件 | 主显 | 小号等宽字跟随（这里是"精确配置"处，双名不挤且有用） |
| 工具栏快捷条件浮层 | 主显 | 只在 tooltip 里 |
| 列选择器 | 主显 | 开关打开时跟随 |
| 抽屉搜索框 | 中文名与 `c_xx` **都能命中** | |
| 视图导航 | 视图也有中文名（`View_PostingOfficeData` → 历任官职） | 灰色小字跟随 |

标签存在 `columns_zh.py`，两层结构解决**同名异义**：

```python
COLUMN_LABELS = { "c_title_chn": "出处文献名", ... }        # 全局默认
VIEW_OVERRIDES = {
  "View_BiogTextData": { "c_title_chn": "著作名" },         # 这一张表里它是著作名
  ...
}
```

覆盖统计：**396 个不同列名 / 713 个「视图.列」组合，无遗漏**；
其中 41 个列名确实存在跨视图歧义，全部由 `VIEW_OVERRIDES` 覆盖。

改标签不用重跑剖析：`python web/build_view_meta.py --labels-only`（不连库，1 秒）。

## 9. 这一轮之后仍然存在的取舍

- 表头 tooltip 仍然覆盖了每一列（虽然只是 hover 才出现）。若日后觉得噪音大，
  可只对「中文名与列名差异大」的列挂 tooltip，其余靠「列名」开关。
- 导航条的 ⊞ 浮层里，搜索会扫过全部 24 个视图的 ~700 条列标签（纯前端），
  数据量再涨 10 倍时需要改成索引。
- 结果表仍是 `nowrap + 省略号`；研究建议的「单元格内容悬浮展开」还没做。
